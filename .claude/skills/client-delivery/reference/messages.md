# Client messages

## Reply first, work second

When a pasted client message needs a reply that doesn't depend on the work being finished (an acknowledgement, confirming terms, "starting now", answering a question), the draft reply is the first output, in a code block, before any work starts. The user can answer the client straight away and let the work run.

Ask "start the work?" only if the go-ahead is unclear. Otherwise draft, then go.

## Draft after edits

A reply that reports finished work ("it's done, here are the links") waits until every edit in that round is done and verified. No drafts in progress updates. If something is still open, name it and ask; hold the draft until it's settled. A reply drafted before the edits end goes stale and the user has to re-read it.

## The thread audit

Before building a page from a client's document, check the thread for a later version of it. Before calling a milestone done, walk the whole thread for every promise and attachment. List each promise with its live status. Building from notes instead of the thread silently drops client content, and the client notices.

If the thread isn't in front of you, ask the user to paste it, or to check the downloads folder against every attachment named in it.

## The closing question

A message ends with one easy yes/no question only when the user is trying to convert the buyer:
- a prospect who hasn't hired yet
- a follow-up or nudge
- an upsell or future-work pitch
- the post-delivery ask for the next milestone or a review

Working replies on an active job (status updates, answers, deliveries) end naturally. A question goes in only when there is something real to ask (an access request, a choice they must make). Never a tacked-on "Shall I start the work you already agreed?".

When a closing question is used:
- no time or day in it (no "this week", "by Tuesday", "tomorrow"); a real deadline can sit in the body
- never "whenever you're ready", "just say", "happy to when you want", "let me know"
- never "now" to a prospect who hasn't hired; it reads pushy

The contract itself is asked for once. After that, follow-ups lead with value and easy questions, never the contract again.

Good: "Shall I put the banner live?" / "Would you rather I start with the checkout or the product pages?"
Bad: "Let me know whenever you're ready to proceed." / "Shall I start this week?"

## The contract close message

Trigger: the user says "let's end this contract" or similar, meaning it has run its course. The upsell, future-work and open-ask nudges got no answer or a no, and nothing else is coming. It does not mean "this milestone is done, the next one starts". If it's unclear which they mean, ask.

The message, in this order, short paragraphs, under 500 characters:
1. Acknowledge their last word or decision.
2. Say plainly that what was built does its job for them (value, not a pitch).
3. Leave the door open with one concrete, low-effort offer tied to the work just done.
4. Optionally hand the next move to them. No question that demands an answer, no contract talk, no new pitch.

Example (invented):

```
Makes sense, Priya.

The new enquiry form covers what your customers actually ask for, so the page is doing its job. Let me know how the first month's enquiries look.

If you ever want a tweak to the form or the thank-you page, I can turn it around quickly.
```

After it's sent, note the close in the client's `future-work.md`.

## Client feedback (the public review you leave)

Describes the client as a person and how working together went: responsiveness, communication, trust, openness, prompt payment, would work again. Three to five short sentences, warm and specific to their manner. No list of what was built, no numbers. A project summary reads like a case study and tells the next freelancer nothing useful.

## Always

- Everything the user copies goes in a fenced code block, one per message, with the character count beside it.
- The client voice from `context/client-voice.md`. Plain words, one idea per paragraph, no em dashes.
- No price in a message the user hasn't set a price for. No timeline unless the user gave one.
- Never claim work that isn't recorded in the proof bank or the client's folder.
- No calls or video unless the user offers them; a timed live chat in the platform's room, with the substance written first, is the default alternative.
